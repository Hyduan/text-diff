# 开发与发布流程

项目采用轻量 GitHub Flow：日常开发通过 PR 验证和合并，发布通过明确的版本提交与标签管理。本文约定流程顺序，不代替当前环境中的 Git 操作授权规则。

## 当前能力与待实现部分

| 流程 | 状态 |
| --- | --- |
| 目标为 `main` 的 PR、推送到 `main`、手动触发检查和构建 | 已配置 `Build` 工作流，配置推送到 GitHub 后生效 |
| Windows 安装版、Windows 便携版、macOS Apple Silicon / Intel 安装包 | 已配置为 Actions Artifacts，保留 14 天 |
| 推送版本标签后构建并上传到 Draft Release | 待实现 |
| 自动核对标签与应用版本、识别 Pre-release | 待实现 |
| 发布者签名、macOS 公证、应用自动更新 | 待实现 |

当前工作流不会因为推送版本标签而自动发布。下面的“发布版本”约定了 Release 自动化实现后的操作方式；启用前仍需补齐工作流并验证。

## 日常开发

1. 检查工作区与当前分支，保留已有修改；从更新后的 `main` 准备短期任务分支。功能用 `feat/`，修复用 `fix/`，文档用 `docs/`，构建和维护用 `chore/`，例如 `chore/github-actions`。
2. 完成一个明确任务，运行与改动匹配的检查，按 Conventional Commits 提交。完整检查命令见 [README](../README.md#检查与构建)。
3. 推送任务分支并创建目标为 `main` 的 PR。当前配置不在普通任务分支 push 时触发，创建或更新 PR 后才自动检查和打包。
4. 审阅最终差异与 CI 结果；有桌面行为变化时，下载 Actions Artifacts，在对应系统上验收。浏览器测试不能替代原生窗口与安装包验证。
5. 检查通过且任务完成后 Squash merge，合并标题遵循 Conventional Commits。主分支上的构建也应通过。
6. 需要继续开发时安全同步本地 `main`；获准清理分支后，确认内容已合入，再删除本地和远程任务分支。

`main` 保持可构建、可验证，但每次合并不必发布版本。日常测试包从 Actions 下载，正式版本从 Release 下载。

## 准备版本

1. 确定本次发布范围与版本号。从更新后的 `main` 准备版本分支，例如 `chore/release-0.1.0`。
2. 统一以下应用版本号，文件中的版本不带 `v` 前缀：

   | 文件 | 字段 |
   | --- | --- |
   | `package.json` | `version` |
   | `src-tauri/tauri.conf.json` | `version` |
   | `src-tauri/Cargo.toml` | `[package].version` |
   | `src-tauri/Cargo.lock` | 根包 `text-diff` 的 `version` |

   通过 Cargo 工具刷新根包的锁文件记录，检查差异，避免为更新版本号顺带升级依赖。仅当依赖或包管理配置确实变化时更新 `pnpm-lock.yaml`。
3. 更新仓库根目录的 `CHANGELOG.md`，记录新功能、修复、行为变化与已知限制；首次发布时创建该文件。版本号已经是目标值时无需重复修改，但仍应核对一致性。
4. 创建版本 PR，说明发布范围和验证结果。所有检查通过，确认更新日志与实际改动一致后合入 `main`。
5. 记录合入后的版本提交 SHA。后续标签应指向这个提交；若 `main` 已继续前进，不把标签直接打在最新提交上。

### 版本约定

| 情况 | 示例 |
| --- | --- |
| 修复问题 | `0.1.0` → `0.1.1` |
| 增加功能；在 `0.x` 阶段包含不兼容变更时，必须在更新日志中明确说明 | `0.1.0` → `0.2.0` |
| 进入稳定版本 | `0.x` → `1.0.0` |
| 稳定版本后的不兼容大改动 | `1.x` → `2.0.0` |
| 测试版本 | `0.2.0-beta.1`，发布为 Pre-release |

Git 标签使用 `v` 前缀，例如应用版本 `0.1.0` 对应标签 `v0.1.0`。

## 发布版本（自动化待实现）

1. 确认版本提交已合入远程 `main`、对应 CI 通过，且标签版本与上述应用版本一致。
2. 在已确认的版本提交上创建附注标签，例如 `v0.1.0`。获准推送该标签后，只推送指定标签，不批量推送本地标签。
3. Release 工作流应检出标签对应的提交，重新执行检查和跨平台构建；标签版本不一致或提交未合入 `main` 时应失败。不能直接复用其他提交的构建产物。
4. 将以下产物上传到同一标签对应的 Draft Release，发布说明使用该版本的更新日志。资产名称应包含版本、系统和架构，明确区分安装版和便携版：

   - Windows x64 NSIS 安装程序。
   - Windows x64 便携版 ZIP，解压后运行应用，依赖系统 WebView2 Runtime。
   - macOS Apple Silicon DMG。
   - macOS Intel DMG。

5. 保持草稿状态，确认所有平台任务成功、四类产物齐全且对应同一版本。下载草稿资产验证安装、启动、文本对比、差异跳转，以及 Windows 便携版直接运行；安装版还需检查卸载。缺少某个平台的验收时记录为待验收，不能视为全部通过。
6. 检查发布说明中的已知限制；未签名、未公证等影响运行的事项应说明。测试版本同时标记为 Pre-release，正式版本按稳定版本发布。
7. 完成人工验收并获得明确发布授权后，将草稿发布为公开 Release。推送标签只触发草稿构建，不自动公开发布。

## 构建失败与发布后修复

- 检查、构建或上传失败时保持草稿，不发布缺少产物的版本；网络等临时错误可以重跑同一标签的工作流。
- 自动化需要支持重跑时复用同一标签的草稿，避免重复创建 Release。公开发布前核对最终资产；不要在用户验收过程中无提示替换资产。
- 如果修复需要修改代码或版本配置，通过新 PR 合入，使用新的版本号与标签，避免移动已有版本标签。
- 已公开的版本保持标签和安装包不变。发现问题后记录已知问题，修复并发布新版本；必要时在旧 Release 说明中引导用户使用修复版本。

## Release 自动化启用条件

实现 Release 工作流时应满足以上约定，至少覆盖标签版本核对、提交归属检查、四类产物上传、草稿与 Pre-release 设置、重跑行为，以及失败时不公开发布。完成一次测试版本的完整演练后，再用于正式版本发布。
